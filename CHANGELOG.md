# Changelog

## [Unreleased]

### Added

- Initial release: `Scry.Engine.Ch` -- a real, kind-independent `Scry.Core.EngineBehaviour` implementation over ClickHouse via the `ch` driver, modeled on `scry_engine_exqlite`/`scry_engine_duckdbex`'s own single-authoritative-`execute/3` architecture. Closes the validation lang_spec.md §12 already commits to (the time-series kind, framed around "the RabbitMQ/ClickHouse use case") -- `scry_time_series`'s own `LAST`-lowering already rewrites into an ordinary `WHERE` predicate before any engine sees it, so no time-series-specific code was needed here, only a correct general engine.
  Every driver-specific claim was confirmed empirically against a real ClickHouse server (a local Docker container, `CLICKHOUSE_SKIP_USER_SETUP=1` required as of ClickHouse 25.1 for the stock image's `default` user to have network access at all) before being designed around. Several real, confirmed differences from this package's SQL-engine siblings: ClickHouse has no untyped bind placeholder at all -- every parameter needs its own ClickHouse type spelled out inline (`{$0:Int64}`, `{$1:String}`, ...), zero-based (`WhereTranslator` threads a running counter through the whole predicate tree, confirmed by property test); `ch` is `DBConnection`-based, a real linked pool process, not a bare native handle; nullability is inverted (`NOT NULL` by default, `Nullable(...)` opts in); `ch`'s own query function returns one fully-materialized result per call with no validated chunked-fetch API, so `execute/3` is always eager, never a lazy `Stream`, unlike its embedded siblings; and `MergeTree` (ClickHouse's own standard table engine) has no guaranteed row order without an explicit `ORDER BY` -- found running this package's own test suite against a correlated nested `SELECT`, not assumed, and fixed by giving that query its own `order_bys` rather than relying on incidental storage order.
  **The one genuinely load-bearing finding**: ClickHouse's own `Bool` type is `UInt8`-backed and compares numerically equal to a plain integer (`SELECT {$0:Int32} = {$1:Bool}` with `(1, true)` returns `true`, confirmed directly) -- a real silent-wrong-result risk `Scry.Core.QueryOps`'s own `Kernel.==/2`-based interpreter semantics don't share (`1 == true` is `false` there). `WhereTranslator` has no schema visibility at translation time to tell a genuinely `Bool`-typed column apart from an ordinary integer one a boolean literal would silently mismatch against, so it declines every boolean `WHERE` literal outright -- unlike `scry_engine_duckdbex`, which found DuckDB's own equivalent bound-parameter binding safely strict enough to allow booleans through unconditionally. Every other type mismatch (a non-numeric string against an `Int32` column, e.g.) is a real, clean `TYPE_MISMATCH` server error, confirmed directly, so this compiler collects no schema-level type-affinity check at all beyond that one boolean exception -- consistent with `scry_engine_duckdbex`'s own finding that ClickHouse (like DuckDB, unlike SQLite) never silently produces a wrong comparison result for a genuine type mismatch.
  A `DateTime.t()`/`NaiveDateTime.t()` literal binds natively (`ch` accepts the Elixir struct directly, confirmed, unlike `scry_engine_duckdbex`'s own string-based workaround for `duckdbex`) as `DateTime64(6)` (microsecond precision) regardless of the value's or the compared column's own actual precision -- confirmed directly that a `DateTime64(6)` parameter compares correctly against an ordinary second-precision `DateTime` column. The `NOT NULL` check runs immediately before the compiled query, not inside a shared transaction with it, since ClickHouse has no standard multi-statement transaction concept over its HTTP interface at all -- a real, honestly-stated gap relative to the atomic guarantee `scry_engine_exqlite`/`scry_engine_duckdbex` both offer, not a papered-over one.
